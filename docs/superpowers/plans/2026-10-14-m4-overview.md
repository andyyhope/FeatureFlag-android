# M4 (samples, docs, CI, release): overview and contract

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement the two sub-plans below task-by-task, in order (A1→A5, then B1→B8). Steps use checkbox (`- [ ]`) syntax for tracking.
> This file itself is not a task list. It is the **contract** shared by the two M4 sub-plans. Read it before any task. Every sub-plan task implicitly includes the Global Constraints below, and must use **exactly** the names, paths and ids in the Contract section. A task may add private or internal helpers; it may not rename anything here.

**Goal:** Make the library usable by someone who has never seen this repo:
- two sample apps (a host and a companion) that run the iOS demo's story end to end on a device;
- a README and `docs/*.md` whose code is compiled and run by a test;
- CI on every PR, including the device suites;
- a release that is ready to publish to Maven Central but is not published.

**Architecture:**
- **Samples first (M4a).** They exercise the library from the outside, as a consumer would. They prove KSP in an Android app. They also give the docs real manifest and Gradle files to quote, and they run the end-to-end device check that M3 deferred.
- **Then freeze and describe (M4b).**
  - A short pre-freeze API pass.
  - Publishing (vanniktech + Dokka + a BOM).
  - ABI dumps, which freeze the public API from then on.
  - A `:docs-samples` module whose `DocsSyncTest` keeps every doc snippet byte-identical to compiled, tested code.
  - The docs themselves.
  - Three GitHub Actions workflows.

- Everything in the M1–M3 overviews' Global Constraints still applies, except as changed below. That covers:

- **No version bumps.** Gradle 9.5.1, AGP 9.1.1, Kotlin 2.2.10, KSP 2.2.10-2.0.2, Compose BOM 2026.01.00 and the rest stay as they are.

## Review Focus

These are the inputs and conditions the spec implies but no single task's happy path exercises. Each is pinned in the task that owns the code.

1. **A companion signed with another key, installed next to the trusted one.** It must install alongside it, connect to the same host, and show `PermissionDenied` with both certificate digests. It must not show `HostNotFound` or crash.
   - Pinned by A4's merged-manifest and signing-report checks and A5's device step.
2. **A signal sent to a host that is not running.** After `adb shell am kill`, the host must cold-start and report handled, and its pole must be wired before the provider answers.
   - Pinned by A2's test that `Application.onCreate` publishes the schema and registers every observer, and by A5's device step.
3. **A release-version dry run with no signing key.** `publishToMavenLocal -PVERSION_NAME=0.1.0` must succeed unsigned, and the same command with a key must produce `.asc` files.
   - Pinned by B2's verification commands.
4. **Docs that drift from code.** `DocsSyncTest` must fail on each of these:
   - an unmarked fence;
   - a snippet whose region changed;
   - a region nobody cites;
   - a broken relative link;
   - an `output` block that no longer matches.

   Pinned by B4's checker tests against fixture markdown, before any real doc exists.
5. **An ABI check that silently checks nothing.** Each of the six published library modules must have a committed dump. `./gradlew check` must run all six checks, and CI must fail if a check task is missing.
   - Pinned by B3's mutation check and B8's explicit task list.

## Deviations from the spec

1. **`samples/signals` is a shared JVM library.** It holds `AppSignal` and `CacheSignal`, which host and companion both depend on, like iOS compiling `AppSignals.swift` into both targets. It is not a third app: the spec's module table names it, but iOS has no third example app. The Live Activity widget is already a notification inside `featureflag-ui`.
2. **The ABI check is BCV on the JVM modules and `android-bcv-bridge` on the Android ones.**
   - The tasks are `apiCheck` (JVM) and `releaseApiCheck` (Android). Both run in `check`.
   - The spec's `./gradlew check apiCheck` therefore becomes `./gradlew check`.
   - Updating dumps is `./gradlew apiDump releaseApiDump`.
   - Kotlin's built-in ABI validation does not support Android libraries yet (KT-78025).
3. **`docs-samples` is an Android library module** (Robolectric + KSP in unit tests; spike-ksp). It is not JVM-only, because about half the snippets need `Context`, the bridge or Compose. All its code is in `src/test`.
4. **The release is prepared, not published.**
   - `release.yml` dry-runs to Maven local on a tag or a manual run.
   - Its publish job only runs when four things are all true: it was dispatched manually, on a `v*` tag ref, the repository variable `PUBLISH_ENABLED` is `true`, and the run is in the protected `maven-central` environment.
   - THE USER does the Sonatype namespace, the DNS TXT record, the keys, the secrets and the first publish.
5. **The pre-freeze API pass is narrow (B1).**
   - `FlagPole.apply(payload)` becomes `FlagPole.applyPayload(payload)`.
   - The scaffolding placeholders `FeatureFlag` (`VERSION`) and `TestFeatureFlags` are deleted, along with their smoke tests.
   - Any constant the dumps show as accidentally public is made `internal`/`private` (for example `ATTEMPTS`, `HEX_DIGITS`).
   - The companion's Signals footer, ported from iOS ("The app has to be running to hear it"), is false on Android. It becomes "Sent the moment you tap. If the app isn't running, Android starts it to deliver the signal."
   - The other naming-drift items in `notes/2026-10-09-m1-followups.md` are left as they are and listed as a follow-up for THE USER before the first publish.
6. **The end-to-end check is run by the controller with `adb` on `Pixel_7`,** following the spec's recipe plus M3's deferred items. It is recorded in this overview, not automated: a two-APK, two-signer instrumented test would need its own test harness, which is out of scope.
7. **Doc snippets are checked byte for byte.** iOS hand-mirrors its doc examples in tests. Here `DocsSyncTest` compares each fence to a region of compiled, executed code. It also compares `output` fences to values computed at test time.
8. **No `samples` instrumented tests.** The samples' unit tests (Robolectric) and A5's manual check cover them. The library's two device suites stay the CI device job.

## Contract

### Build plumbing (A1)

- **Catalog plugin `android-application`:** `com.android.application`, `version.ref = "agp"`. The root declares it `apply false`.
- **`featureflag.android-application`** (class `AndroidApplicationConventionPlugin`) applies `com.android.application` and `featureflag.detekt`, and sets:
  - `compileSdk 36`, `minSdk 26`, `targetSdk 36`, Java 17;
  - via `KotlinAndroidProjectExtension`: `jvmToolchain(21)`, jvmTarget 17, `allWarningsAsErrors`;
  - no `explicitApi()`, no `featureflag.fixtures`;
  - unit tests with Android resources included, and the same Robolectric/JUnit test dependencies as the library convention.
- **`featureflag.compose`** configures `CommonExtension` (`buildFeatures.compose = true`), so it applies to libraries and apps alike. `featureflag-ui` is unchanged in behaviour.
- **One source of truth for the host id:** `gradle.properties` gets `featureflag.sample.hostId=com.andyyhope.featureflag.sample.host`. It feeds:
  - the host's `applicationId`;
  - the companion's `manifestPlaceholders["hostId"]` (for `<uses-permission android:name="${hostId}.permission.FEATURE_FLAG_BRIDGE"/>`);
  - the companion's `BuildConfig.HOST_PACKAGE`.

### `:samples:signals` (A1)

- Directory `samples/signals`, plugin `featureflag.jvm-library`. Its `explicitApi()` is fine for a tiny library.
- Package `com.andyyhope.featureflag.sample.signals`, `api(project(":featureflag-core"))`.
- `public enum class AppSignal : FlagSignal { RefetchRemoteConfiguration, ClearRemoteConfiguration }`, with descriptions "Re-fetch remote configuration" and "Clear remote configuration".
- `public enum class CacheSignal : FlagSignal { PurgeImageCache, PurgeEverything }`, with descriptions "Purge the image cache" and "Purge everything"; `requiresRestart` is true only for `PurgeEverything`.
- Wire names are the Kotlin entry names (PascalCase). Nothing outside the samples depends on them.

- **Dependencies:**

  - `implementation(project(":samples:signals"))`;

  - Compose from the BOM, as in `featureflag-ui`;
  - `activity-compose` and `lifecycle-runtime-compose` (nothing needs `lifecycle-viewmodel-compose`).
- **Flags:** a port of iOS `AppFlags.swift`, starting from `featureflag-core/src/test/.../scenario/DemoFlags.kt`.
  - Container names are as on iOS: `AppFlags`, `CheckoutFlags`, `ExpressFlags`.
  - Apple Pay is renamed to Google Pay throughout:
    - the property `googlePay` (key `checkout.google-pay`);
    - remoteKey `featureToggles.checkout.googlePay`;


  - calls `publishSchema(this)`;
  - registers one `FlagSignalChannel.host.observe` per signal enum, as on iOS;

  All of this happens before `onCreate` returns. The provider's startup barrier relies on that.
- **Screen (A3):** one Compose screen, title "Demo", with iOS `ContentView`'s seven sections in order and the same strings, except for the rewordings the M4a plan lists:

- BCV is applied at the root (not `apply false`), with `apiValidation`:

### `:docs-samples` and `DocsSyncTest` (B4)

- Directory `docs-samples`.
- Plugins `featureflag.android-library`, `featureflag.compose`, `ksp`, with `kspTest(project(":featureflag-ksp"))`.
- All code is in `src/test/kotlin/docs/<doc>/` (package `docs.<doc>`, one package per document, so the generated `…Spec` names never clash). Test dependencies are the published library modules.
- **Markers in markdown** are an HTML comment on the line immediately before a fence:
  - `<!-- snippet: <name> -->`: the fence body equals the Kotlin/kts/XML region `<name>`;
  - `<!-- output: <name> -->`: the fence body equals the string a test registers under `<name>`;
  - `<!-- snippet-ignore: <reason> -->`: deliberately unchecked.
  - Names match `[a-z0-9-]+`.
  - `sh`, `bash`, `console` and plain-text fences need no marker.
- **Markers in sources:**
  - `// region snippet: <name>` … `// endregion` in `.kt`/`.kts`;
  - `<!-- region snippet: <name> -->` … `<!-- endregion -->` in `.xml`.
- **Comparison:** take the lines strictly between the markers, remove their common indent, turn `\r\n` into `\n` and trim trailing blank lines. The result must equal the fence body exactly.
- **Scanned files:**
  - markdown: `README.md`, `docs/*.md`, `samples/README.md`;
  - sources: `docs-samples/src/**`, `samples/**/src/**`, `samples/**/build.gradle.kts`.
- **Output registry:** `docs.DocOutputs`, a `Map<String, () -> String>` in `docs-samples` test code, filled by the doc tests.
- **`DocsSyncTest` fails on:**
  - an unmarked kotlin/kts/xml/json fence;
  - a missing or duplicate region;
  - text that differs (the failure shows a unified diff with both locations);
  - an orphan region;
  - a mismatched output;
  - unbalanced markers;
  - a relative link to a missing file or heading anchor.

  Regions named `snippet-support:<name>` are exempt from the orphan rule.
- **Gradle wiring:** markdown and source roots reach the test as system properties and are declared as task inputs, the same way `featureflag.fixtures` does it, so editing a doc re-runs the test.

### CI (B8)

- **`.github/workflows/check.yml`** runs on `pull_request` and on pushes to `main`:
  - Runner `ubuntu-latest`, JDK 21 Temurin, `gradle/actions/setup-gradle@v6` with `cache-provider: basic` (writing to the cache only on `main`), a Robolectric jar cache.
  - It runs `./gradlew build detekt`, then `./gradlew :dokkaGeneratePublicationHtml`. A guard step lists the six expected check tasks and fails if any is missing.
  - Reports are uploaded `if: always()`.
- **`.github/workflows/instrumented.yml`** runs on the same triggers:
  - KVM udev rule, `reactivecircus/android-emulator-runner@v2`, API 36 `google_apis` `x86_64`, an AVD cache.
  - It runs `./gradlew :featureflag-bridge:connectedDebugAndroidTest :featureflag-ui:connectedDebugAndroidTest`.
  - It does not ignore any paths, so docs-only PRs also run it.
- **`.github/workflows/release.yml`:**
  - The `dry-run` job runs on a `v*` tag or a manual run. It does `publishToMavenLocal` into a job-local directory, with `-PVERSION_NAME` taken from the tag, and uploads the artifacts.
